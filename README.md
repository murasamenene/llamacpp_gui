# llama.cpp 启动器（llamagui）

一个**零依赖**的 tkinter 图形界面，用来配置、启动、观测本机的 llama.cpp
推理服务。

- 只用 Python 标准库：`tkinter`、`subprocess`、`threading`、`urllib`、`json`。
  **不需要 pip install，不需要虚拟环境。**
- 不修改、不重编译 llama.cpp：界面直接驱动同目录下的发行版二进制。
- 启动按钮绑定 `llama-server`；就绪后一键打开它**自带的官方 Web UI**，
  日常对话、多轮会话、图片输入都由那个界面完成，本工具不做重复实现。

---

## 快速开始

```
双击  F:\llama.cpp\gui\start.bat
或    pythonw F:\llama.cpp\gui\llamagui.pyw
或    cd F:\llama.cpp\gui && python -m llamagui
```

推荐 `start.bat`：它会按 `pyw.exe` → `pythonw.exe` → `py.exe` → `python.exe`
的顺序找一个**有 tkinter 的窗口版解释器**，因此**全程不会弹出黑色控制台窗口**。
只有在最后两个回退分支下才会出现控制台（那时保留它是为了让你能看到错误信息）。

`llamagui.pyw` 也可以直接双击，前提是 `.pyw` 已关联到 `pythonw.exe`
（官方 Python 安装包默认如此）。若不确定，用 `start.bat`。

> **不要把 `start.bat` 改成含中文的版本。**
> cmd.exe 按字节偏移解析批处理文件，遇到多字节字符会丢失位置，进而把注释行的
> 片段当作命令执行（曾出现 `'m' 不是内部或外部命令` 这类报错）。因此该文件
> **必须保持纯 ASCII + CRLF**，所有中文说明只放在本 README 里。
> 测试套件中有 7 项断言专门守护这一点。

首次启动会自动完成三件不涉及模型加载的探测：

1. 定位 llama.cpp 目录（见下）；
2. 运行一次 `llama-server --help` 解析出本 build 支持的**全部参数**
   （并存到 `config/cache/help_server.txt`，之后直接读缓存）；
3. 检查必需/可选二进制与 CUDA 运行库是否齐全，结果打印在「控制台」页。

### 目录定位

界面按顺序尝试：自身所在目录 → 上级目录 → 当前工作目录。
找到含 `llama-server.exe` 的那个即为安装目录。

如果整棵目录被移动过，或想把界面放到别处，在 `gui/install.json` 里写：

```json
{ "root": "F:\\llama.cpp" }
```

所有传给子进程的路径都是绝对路径，工作目录固定为二进制所在目录，
因此从任何位置启动都不会出现「找不到模型」这类相对路径问题。

## 四个关键设计

### 1. 只发送你显式设置过的参数

llama.cpp 的 `--fit` 会「自动调整**未设置**的参数以塞进显存」。
如果界面把默认值也写进命令行，就等于悄悄关掉了 fit。
所以配置里**只保存用户真正改过的项**，未填写的输入框完全不产生参数。

**清空输入框**就是「交给 llama.cpp 决定」。工具栏右侧的 **「↺ 恢复本页默认」**
（也在「文件」菜单里）一次清空当前页所有已设置的参数，效果等同于逐个清空：
这些参数不再出现在命令行里，由 llama.cpp 与 `--fit` 决定。点击前会列出将被清空的参数
并要求确认；只影响当前页，其他页不变。

- 「模型」页会保留模型文件与 HF 仓库（它们没有默认值，清空只会导致无法启动）；
- 「基准测试」页恢复的是测试选项（-p/-n/-r 等），模型路径保留；
- 「控制台」「API 参考」页没有参数，按钮置灰；
- 服务运行中点击不影响当前进程，重启后生效。

「上下文」「物理批」这类留空的选项，会由 fit 与模型元数据自行决定。

### 2. 显存估算分三部分，且明确标注哪些是估算

选中模型后（只读 GGUF 文件头，**不加载权重**）：

| 分项 | 来源 | 精确度 |
| --- | --- | --- |
| 模型权重 | 全部张量字节和 × 架构系数 | 计算值（系数为经验值） |
| KV cache | `层数 × 上下文 × KV 头数 × (K维+V维) × 类型位宽` | 计算值 |
| 计算缓冲 | 按 `ubatch` 与词表大小估算 | **经验估算，标 `~`** |

其中 KV 计算会正确处理：

- GQA / MQA（按 `head_count_kv` 而非 `head_count`）；
- 滑动窗口注意力（SWA 层的 KV 深度按窗口折算，而不是整个上下文）；
- MLA 架构（只缓存压缩潜变量 + rope 分量）；
- `--no-kv-offload` 时 KV 位于内存，不计入显存；
- `-np > 1` 时统一 KV 与独立 KV 的差别。

面板还会反推**本机显存下可用的最大上下文**，并提供「填入建议上下文」按钮。

> 估算用于在等待数分钟加载失败之前发现问题。真正的权威始终是
> llama.cpp 自己的 `--fit` 与启动日志里的实际分配数字。

### 3. 运行时显示的是真实测量值

界面从服务日志中提取实测数据，与上面的静态估算**分开显示、互不混淆**：

- `服务实际上下文 n_ctx`
- `offloaded N/M layers`
- `KV self size = ... MiB` 及各设备 `model / KV / compute buffer size`
- `prompt eval time` 与 `eval time` 的 tokens/s → 状态栏右侧

状态栏右侧那组 t/s 就是你当前配置下的真实性能，不需要额外跑基准测试。

### 4. 安全护栏

`--tools`、`--agent`、`--ui-mcp-proxy`、`--mcp-servers-*` 会让服务端读写
本机文件、执行 shell 命令。因此：

- 这些选项默认全部关闭，并集中在「安全（谨慎）」红色区块；
- 当**非本机监听地址**与其中任一项同时出现时，界面**拒绝启动**并说明原因；
- 单独使用非本机地址只给警告。

另外，本 build 中已移除的参数（如 `--draft`）即使出现在旧预设里也不会被发送，
而是记录到控制台，避免 llama-server 因未知参数直接退出。

## 配置与文件

全部状态都在 `gui/config/`，与 llama.cpp 的二进制完全隔离，
llama.cpp 升级或重装都不会丢配置：

```
gui/config/
├─ config.json          当前参数、窗口位置、最近模型、每模型覆盖
├─ presets/*.json       命名预设（可导入导出，便于分享）
├─ cache/                help_server.txt、devices.json、version.json（可随时删除）
└─ logs/                 launch-YYYYmmdd-HHMMSS.txt 每次启动的完整原始日志
```

写盘采用临时文件 + 原子替换，保存过程被打断不会破坏已有配置；
配置文件损坏时会自动改名为 `config.json.corrupt` 并以默认值启动。

### 预设

- 「文件 → 另存为预设」把当前所有**已设置**的参数存成命名预设；
- 「载入预设」整体替换当前参数；
- 「导入/导出预设文件」用于在机器之间搬运。

## 进程生命周期

启动后通过 `GET /health` 判定状态（`503` = 正在加载，`200` = 就绪），
不依赖日志文案，因此升级 llama.cpp 不会破坏判定。

停止按阶梯升级，每一步都写进控制台：

1. **优雅请求**——仅当调用方提供了可用的机制时才执行，执行后等待其自行退出；
2. **`CTRL_BREAK_EVENT`**——仅当子进程真的有控制台时才尝试；
3. **`terminate()`**（TerminateProcess）——本配置下真正生效的手段，立即完成；
4. **`taskkill /PID <pid> /T /F`**——最终兜底。

### 为什么没有"优雅退出"

本启动器用 `CREATE_NO_WINDOW` 启动子进程，**该标志会让子进程完全没有控制台**
（不是"隐藏的控制台"），而 `pythonw.exe` 起的 GUI 自身也没有控制台。
`GenerateConsoleCtrlEvent` 要求调用方有控制台、目标也挂在某个控制台上，
两者都不满足，所以发送 `CTRL_BREAK_EVENT` 必然失败：

```
[gui] 发送 CTRL_BREAK_EVENT 失败：[WinError 6] 句柄无效。
```

这是 Windows 的结构性限制，不是偶发故障。要让它可用就必须给子进程分配控制台，
也就是会**弹出控制台窗口**——正是本启动器要避免的。llama-server 自身也没有
提供关闭用的 HTTP 端点。因此实际生效的是 TerminateProcess。

**代价**：进程不会执行退出清理。对本工具的实际影响极小——显存由操作系统回收，
端口立即释放，日志由本工具自己按行落盘。仅有依赖退出时写盘的功能会受影响，
例如 `--lookup-cache-dynamic`（查找解码缓存）与手动触发的
`POST /slots/{id}?action=save`；本工具不使用前者，后者需要你主动触发。
如果你要用这些功能，建议停止前先手动保存。

### 响应性

**停止与重启都在工作线程上执行，界面不会卡住。** 点击「停止」后会立刻显示
「正在停止…」并禁用按钮，正常路径 **100 毫秒以内**完成。
重启会在停止结束后自动等端口释放再启动，不会误弹「端口被占用」。

关窗时会先确认并停止服务，同样不阻塞界面；另有 20 秒兜底定时器，
保证即使某个线程卡死窗口也会关闭，且不会留下孤儿进程。
子进程以 `CREATE_NO_WINDOW` 启动，所以不会有黑色控制台窗口闪现。

控制台输出由独立线程读取，队列有上限（满时丢最旧行）——
即使日志暴涨也不会阻塞子进程的管道，更不会把内存吃光。
界面最多保留 2 万行显示，磁盘上的原始日志始终完整。

## API 用法

就绪后服务地址形如 `http://127.0.0.1:9931`，OpenAI 兼容基地址是
`http://127.0.0.1:9931/v1`。
端口留空时使用当前 build 的默认端口（旧版 8080，新版 9931，以 `--help` 为准）；
界面始终以服务日志中 `listening on` 报告的实际地址为准。若设置了 `--api-key`，需要
`Authorization: Bearer <key>`。

```bash
curl http://127.0.0.1:9931/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"local","messages":[{"role":"user","content":"你好"}]}'
```

```python
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:9931/v1", api_key="sk-no-key-required")
```

「API 参考」页会根据当前配置自动生成对应的地址与示例，并可一键复制。
该页还提供两个实测按钮：**连接检测**（`/health`）与
**API 自检**（发送一次 1 token 的流式请求，验证整条链路）。

## 常见问题

**双击后弹出一个黑色窗口并报 `'m' 不是内部或外部命令`**
这是 `start.bat` 被写入了非 ASCII（中文）字符导致的 cmd.exe 解析错位，
典型表现就是报错里出现单字母或乱码片段。当前版本的 `start.bat` 已改为纯
ASCII + CRLF，请勿再往里加中文注释；中文说明写在本文件里。

**双击后出现控制台窗口**
说明用到了 `py.exe` / `python.exe` 回退分支（它们的控制台不会自动隐藏）。
确认 `pyw.exe` 或 `pythonw.exe` 在 PATH 上，或直接运行
`pythonw "F:\llama.cpp\gui\llamagui.pyw"`。控制台里的内容可直接忽略，
GUI 本身不受影响。

**端口被占用**
启动前会检测；被占用时弹窗询问是否改用下一个可用端口。
检测采用 bind 探测而非 connect 探测——Windows 上「已绑定未监听」的端口会静默
丢弃 SYN，connect 探测既不准又要等超时。

**显存不足 / 加载失败**
控制台会给出最后 25 行输出和一条原因判断。常见处置：降低 `-c`、
把 `-ctk -ctv` 改为 `q8_0`、调小 `-ub`、MoE 模型加 `-ncmoe`，
或把 `-ngl` **清空**交给 `--fit` 自动决定。

**无法解析 `--help`**
「运行 → 刷新参数表」可重新读取。若仍失败，界面仍可用，但只会发送
参数表中已确认存在的选项。

**想看完整命令行**
「命令预览」显示单行命令，「详情」显示换行排版后的命令与环境变量。
两者都是最终会传给 `llama-server.exe` 的内容，可复制到终端复现。

## 开发

```bash
cd F:\llama.cpp\gui
python -m unittest discover -s tests -t . -v
```

测试**不加载模型、不启动服务**，全部是纯逻辑与界面构造测试：

- `tests/test_core.py` — 帮助文本解析、GGUF 头解析、显存估算公式、
  参数表与命令构造、配置与预设读写、日志解析
- `tests/test_ui_smoke.py` — 真实构造窗口并驱动 Tk 事件循环，
  检查每个参数都有控件、预览随输入更新、预设可往返

其中几项测试专门守护容易回归的地方：

- 参数表中每个长参数都必须存在于本机 `--help` 输出里（升级 build 后不会静默失效）；
- `--no-host` 不得继承紧随其后选项的默认值与 allowed values；
- `--no-kv-unified` 这类「单横线连字符」短参数必须被解析出；
- 未显式设置的参数不得出现在命令行里（保护 `--fit`）。

### 代码结构

```
gui/
├─ llamagui.pyw            入口（pythonw，无控制台窗口）
├─ start.bat               备用入口
├─ llamagui/
│   ├─ app.py              主窗口、状态机、定时器、线程编排
│   ├─ argspec.py          参数元数据表（分组、控件类型、默认值、取值域）
│   ├─ helpparse.py        解析本机 --help（参数存在性的权威来源）
│   ├─ cmdline.py          配置 → argv、跨参数校验、端口探测
│   ├─ gguf.py             只读 GGUF 头解析（纯标准库）
│   ├─ estimate.py         显存 / KV / 最大上下文估算
│   ├─ proc.py             子进程管理、日志读取、停止升级链
│   ├─ logparse.py         ANSI 剥离、JSONL、t/s 与关键事件抽取
│   ├─ httpclient.py       无依赖 HTTP 客户端（health / props / SSE）
│   ├─ config.py           配置、预设、缓存、日志路径
│   ├─ paths.py            llama.cpp 目录定位
│   └─ ui/                 主窗口部件与各页
└─ tests/                  单元测试与界面冒烟测试
```

新增一个参数只需在 `argspec.py` 的表里加一行，
界面会自动出现对应控件；若该 build 不支持，界面会将其置灰并拒绝发送。
